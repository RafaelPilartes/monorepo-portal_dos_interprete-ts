# Step H1 — Staff, versioned configuration, audit; admin login

> Executed inline in continuous mode; independent review at the end of the step.

**Goal:** the team exists (first `super_admin` by script), a configuration version is published and versioned, legal documents and verification document types are editable, the audit trail is visible by level, and `admin-web` logs in with email and password against the local Auth.

**Spec:** `docs/plan/specs/staff-and-config.md` (R-STF-01..03, R-CFG-01..05, R-AUD-01..03, criteria 1–8); `docs/plan/data-model.md` §1 (`profiles`, `staff_members`, `legal_documents`), §4 (`config`), §11 (`audit.events_for_staff`); `docs/plan/api.md` §11.

## Decisions taken here (claude-code-rules.md §3)
- **Minimum of H2 pulled forward** (MASTER-PLAN "O que quebra a sequência" 1): `identity.profiles` and its trigger `identity.handle_new_auth_user` are created in H1, because `staff_members.account_id` and `created_by` reference profiles. Only the columns of data-model §1 and the policy "the owner reads"; H2 adds the rest (column grants, public view, roles).
- **Migration `0002-staff-config.sql`**: `identity.profiles`, `identity.staff_members`, `identity.legal_documents`, `config.platform_versions` (all columns of §4, checks), `config.verification_document_types`. Functions in `functions/` (reapplicable): `auth_helper.account_id` (now requires an active profile and, from H2, accepted terms), `is_staff`, `staff_level`, `account_status`, `staff_level_of`; `identity.set_staff_member`; `config.current_version_id`, `config.get`, `config.require`, `config.create_draft`, `config.update_draft`, `config.publish_version`; `identity.publish_legal_document`; `audit.events_for_staff` (the area of each action is its `entity_type`, mapped to the R-STF-01 matrix in one SQL function `audit.area_of`).
- **Seed** (`seed/0002-config.sql`): version 1 as `draft` with the development values of data-model §4; the four document types (PC-07); empty `terms`/`privacy` drafts (PC-05). `bootstrap-admin.mjs` publishes version 1.
- **Writes by the API** (`api.md` §11): `POST /admin/staff`, `PATCH /admin/staff/:accountId`; `POST /admin/config/versions`, `PATCH /admin/config/versions/:id`, `POST /admin/config/versions/:id/publish` (with `expected_current_version_id`); `POST /admin/legal-documents`, `PATCH …/:id`, `POST …/:id/publish`; `POST`/`PATCH`/`DELETE /admin/document-types(/:id)`. Every write audited (R-AUD-02) inside the same transaction as the change.
- **Reads by RLS through `packages/data`** (`api.md` §16): team list, configuration versions, legal documents, document types, `audit.events_for_staff` (paginated, filters).
- **admin-web:** real `/login` (packages/auth with the Supabase session source), guard `RequireStaffLevel`, "Esta área é só para a equipa do Portal" for a non-staff account; `/team`, `/settings/config`, `/settings/legal`, `/settings/document-types`, `/audit` on real data with the empty, loading and error states of the spec; their mocks deleted.

## Review Focus
1. Two publishes at once: the second gets `STATE_CHANGED`, never two `published` rows.
2. A non-`super_admin` calling any config/team write gets `403 FORBIDDEN` from the API and nothing from the database directly (RLS + grants).
3. Demoting or deactivating the last active `super_admin` → `LAST_SUPER_ADMIN`, also under concurrency.
4. `bootstrap-admin.mjs` refuses any non-local URL and is idempotent; it never prints the password.
5. A staff member sees in `/audit` only the entries of their areas.
