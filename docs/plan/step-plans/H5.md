# Step H5 — Requests core, direct request, chat and the notification bell

> Executed inline in continuous mode, in three parts committed separately (database, API, screens). Independent review at the end of the step.

**Goal:** a requester creates a direct request in the wizard, with the total computed by the database; the invited interpreter accepts or declines; the request becomes confirmed when full; both talk in the request's chat; notices reach the bell and email; unstaffed requests are warned and expire.

**Spec:** `docs/plan/specs/requests-core.md`, `requests-direct.md`, `notifications.md`; `docs/plan/data-model.md` §5; `docs/plan/api.md` §7.

## Decisions taken here (recorded in AD-034)
- **Migration `0007-requests.sql`:** requests, request languages, assignments (with the `EXCLUDE` overlap constraint), threads, messages (append-only), read marks, the request log (append-only), and the immutables guard (`REQUEST_LOCKED`). `ends_at` is set by a trigger: `timestamptz + interval` is not immutable, so it cannot be a generated column.
- **Only the direct request in H5.** `create_request` refuses the other kinds (`VALIDATION_FAILED` on `kind`); the wizard shows "Publicar para intérpretes" and "Pedir à plataforma" as "Disponível em breve" (H7, H11).
- **Message values from SQL:** a refusal that needs a value (START_TOO_SOON's minimum, TOO_MANY_INTERPRETERS's maximum, CANNOT_REDUCE_BELOW_ACCEPTED, INTERPRETER_NOT_ELIGIBLE's reason) sends it in `HINT = 'params:{json}'`; the API fills the catalog message.
- **The preview is an API route** (`POST /requests/preview`), not an RPC: the foundation rule keeps the session's functions to `auth_helper`. The screen never computes a price (`verify.py` check `no-price-arithmetic`); the request status is written only by the allowed functions (check `request-status-writes`).
- **The bell and the chat poll** (30 s and 10 s) instead of Realtime; the bell is in `packages/auth` (the panel layout lives there).
- **Not in H5:** negotiation (proposals, H6), cancellation (H8), `chat_message` email for unread messages, the admin `/requests` screens (H8 with operations), the contacts view (`request_contacts`).

## Tasks
1. Database: migration, functions (price, eligibility, create, invite, accept, decline, reduce, meeting link, expirations, derived status), views, policies, grants, schedule; SQL assertions `0007-requests.sql`.
2. API: routes of api.md §7 used in H5, params from HINT, API integration test; `verify.py` checks with fixtures.
3. Screens: the wizard, `/requests`, `/history`, `/requests/:id` in both apps, the chat, the bell and `/notifications`; Playwright `h5-requests`.
