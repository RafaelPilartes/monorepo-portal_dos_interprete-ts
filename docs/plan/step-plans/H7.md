# Step H7 — The open request, in both modes

> Executed inline in continuous mode. Independent review at the end of the step.

**Goal:** a requester publishes a request for the eligible interpreters, either "first to accept" (at a budget per place, everything included) or "I choose" (interpreters apply at their own price; the requester picks); the eligible interpreters see it in `/open-requests`.

**Spec:** `docs/plan/specs/requests-open.md` (R-OPN-01..05, criteria 1–4, the concurrent one included); negotiation.md criterion 5; data-model.md §5.

## Decisions (AD-036)
- Migration `0009-open-requests.sql`: the candidate's message on the assignment (`application_message`).
- `booking.create_request` opens the `open` kind; the total of "first to accept" is the budget for each place (D-92); "I choose" has no total before the choice; the eligible interpreters get `open_request_new` (Portal only).
- `booking.accept_open_request`, `apply_to_request`, `withdraw_application`, `select_candidate`; the request row lock serialises the places; whoever arrives after the last place gets `SLOTS_FULL`.
- `booking.open_requests_for_me` is a view over `auth_helper.open_requests_for_me()` (the session runs only `auth_helper` functions); `auth_helper.can_view_request` lets the eligible interpreters open a waiting open request (R-REQ-07), private fields still hidden.
- The concurrent criterion runs in the API database tests with three real parallel requests.

## Tasks
1. Database, SQL assertions `0009-open-requests.sql`.
2. API routes (accept, applications, select, withdraw), the concurrent test.
3. Screens: wizard with the open mode and the budget, interpreter `/open-requests`, candidates with "Escolher", "Retirar candidatura"; Playwright `h7-open-requests`.
