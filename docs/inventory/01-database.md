### Padrão transversal: enums por comentário

Nenhum valor restrito é imposto pela base de dados. Em todas as 37 tabelas, colunas como `status`, `type`, `role`, `severity`, `priority` são `TEXT` livre, com os valores válidos escritos apenas como comentário SQL. Exemplo [VISTO] `database_schema.sql:253`:

```sql
status TEXT NOT NULL DEFAULT 'pending', -- pending, accepted, rejected, completed, cancelled, in_progress
```

Consequência: `UPDATE bookings SET status = 'banana'` é aceite pela base de dados. A única validação possível é na aplicação — e a aplicação não a faz (ver `02-screens.md`). **Há exactamente uma excepção**: `reviews.rating INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5)` [VISTO] `database_schema.sql:296`.

### Padrão transversal: `created_at` / `updated_at`

Quase todas as tabelas têm `created_at TIMESTAMPTZ DEFAULT timezone('utc'::text, now())` e `updated_at` idem. Excepções [VISTO]:
- `users` — ambas com `NOT NULL` (as únicas)
- `favorites`, `audit_logs` — só `created_at`, sem `updated_at`
- `interpreter_languages`, `interpreter_specialties` — **nenhuma das duas** (tabelas de junção puras)

**Constraints de tabela** [VISTO] `:303-312`:
```sql
CONSTRAINT reviews_author_check CHECK (
    (author_interpreter_id IS NOT NULL AND author_requester_id IS NULL) OR
    (author_interpreter_id IS NULL AND author_requester_id IS NOT NULL)
),
CONSTRAINT reviews_target_check CHECK (
    (target_interpreter_id IS NOT NULL AND target_requester_id IS NULL) OR
    (target_interpreter_id IS NULL AND target_requester_id IS NOT NULL)
),
UNIQUE(booking_id, author_interpreter_id, author_requester_id)
```

Modelação bidireccional bem imposta: exactamente um autor e exactamente um alvo. Mas [VISTO]:
- **Nada impede auto-avaliação**: `author_interpreter_id = target_interpreter_id` passa os dois CHECKs.
- **Nada liga o autor ou o alvo à reserva**: é possível avaliar uma `booking` em que nenhum dos dois participou.
- O `UNIQUE(booking_id, author_interpreter_id, author_requester_id)` tem sempre uma das duas colunas de autor a NULL (pelo `reviews_author_check`). Em Postgres, dois NULL não colidem num índice único, pelo que **a constraint não impede duplicados**: duas reviews do mesmo requerente na mesma reserva passam. [VISTO quanto ao SQL] / [INFERIDO quanto ao comportamento — não verificável sem base de dados]

## 4. Funções e triggers

### 4.1 `public.handle_new_user()` — `database_schema.sql:25-41`

```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO public.users (id, email, name, avatar_url)
    VALUES (
        NEW.id,
        NEW.email,
        COALESCE(NEW.raw_user_meta_data->>'full_name', NEW.raw_user_meta_data->>'name', 'Novo Usuário'),
        NEW.raw_user_meta_data->>'avatar_url'
    );
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

DROP TRIGGER IF EXISTS on_auth_user_created ON auth.users;
CREATE TRIGGER on_auth_user_created
    AFTER INSERT ON auth.users
    FOR EACH ROW EXECUTE PROCEDURE public.handle_new_user();
```

| Aspecto | Observação |
|---|---|
| Objectivo | espelhar cada registo de `auth.users` numa linha de `public.users` |
| `SECURITY DEFINER` | necessário para escrever em `public.users` a partir do contexto de auth [VISTO] |
| **Não define `role`** | o `INSERT` cobre `id, email, name, avatar_url`. `role` fica NULL. O `signUp` do DAO passa `extraData` para `raw_user_meta_data` (`SupabaseAuthDAO.ts:27-33`), mas a função **só lê `full_name`, `name` e `avatar_url`** — qualquer `role` enviado no registo é silenciosamente ignorado [VISTO] |
| **Não cria perfil** | não insere em `interpreter_profiles`, `requester_profiles` nem `admin_profiles`. Um utilizador recém-registado não tem perfil; e como `interpreter_profiles.bio` é `NOT NULL`, criá-lo depois exige sempre uma bio [VISTO] |
| `search_path` | **não fixado.** Uma função `SECURITY DEFINER` sem `SET search_path` é o padrão que o linter do Supabase sinaliza como `function_search_path_mutable` [VISTO quanto à ausência] / [INFERIDO quanto ao aviso] |
| Sem tratamento de erro | se o `INSERT` falhar (ex. colisão em `users.email UNIQUE`), a transacção de registo em `auth.users` falha inteira [VISTO quanto à ausência de `EXCEPTION`] / [INFERIDO quanto ao efeito] |
